# 恢复、修复与组件更改

Rust 后端提供三种维护操作：恢复处理上一次未完成的事务；修复处理已安装资源缺失或变化；组件更改按新的选择增删应用内容。它们只管理同一当前用户、同一产品的受管资源，用户数据和未知文件保持原样。组件更改需使用当前源码配套构建的工具，已发布 `v0.1.0-preview.1` 不含此能力。

维护能力随本版 runtime 和 worker 一起打入新 Setup；此前生成的安装包不会自动更新。尚未支持维护的旧 Rust 安装，可以先用更高应用版本的新包完成正常升级，再保留该新包用于日后修复。已有中断事务仍须满足恢复证据要求，不能用升级绕过。

当前源码生成的新安装还提供 Windows 系统“更改”入口，打开相同维护页；验证安装目录中的完整离线载荷后，复制运行组件到私有临时目录执行，正常修复和组件更改无需重新寻找 Setup。内部组件或记录不完整时改用原始 Setup；按钮、命令和旧安装迁移规则见[Windows 维护入口](windows-maintenance.md)。

## 怎样选择

| 情况 | 操作 |
|---|---|
| 安装器意外退出，再打开提示上次任务未完成 | 先检查并恢复上次事务 |
| 版本已经安装成功，后来程序文件或快捷方式丢失 | 使用该构建的原始 Setup 修复 |
| 版本不变，需要添加或移除可选内容 | 使用同一构建的原始 Setup 更改组件 |
| 需要安装更高版本 | 使用完整包升级 |
| 应用数据库损坏或应用代码有缺陷 | 由应用处理；安装器不解释应用数据 |

恢复结束后才能开始新的安装、升级、更改组件、卸载或修复。不能通过删除锁、事务标记、日志或备份绕过检查。

## 恢复如何决定动作

恢复先验证当前用户、产品、安装实例、原任务、路径边界、进程身份、互斥状态，以及备份、日志和磁盘上的资源。检查得到的结论必须在执行时再次确认。

| 可确认的状态 | 处理 |
|---|---|
| 原进程仍在运行 | 拒绝并发恢复 |
| 尚未变更受管资源 | 核验原状态并结束遗留事务 |
| 已变更但尚未提交 | 首次安装撤销本次变更；升级、组件更改、卸载、修复恢复到该次操作之前 |
| 已完整提交 | 验证提交后的资源，确认结果并完成收尾 |
| 恢复已经完成 | 重新核验并返回现有恢复结果 |
| 备份缺失、资源冲突、记录不足或身份不符 | 保留现场并报告原因 |

没有最后一条成功日志不等于没有提交。恢复必须结合持久提交证据和实际资源，不能只根据进程退出码或界面进度决定回退。恢复记录与安装 receipt 也有不同用途：前者记录中途变更，后者声明完整提交后的资源归属。

恢复自身的变更也要记录，重复执行时先识别哪些步骤已经完成。确认最终状态后才解除事务阻止。旧版本生成的记录若缺少跨进程恢复所需证据，应明确拒绝，不能猜测补全。

这里的恢复目标是得到可核验的提交前或提交后状态。恢复结束后，如需再次安装或升级，重新发起正常任务。它不负责应用数据库恢复，也不承诺任意断电、存储设备故障或机器重启场景都可恢复。

## 修复需要什么输入

修复使用与原安装清单一致的原始 Setup，或系统维护入口验证后的已安装离线载荷。产品 ID 和版本号相同仍不足以证明是同一构建；manifest、载荷、安装记录、当前用户与目标目录必须一致。

包摘要用于核对内容一致性，不替代发布者身份验证。请保留来自应用发布者的原安装包。receipt 安装记录缺失、损坏或不符合当前支持格式时，修复不能仅凭目录名接管文件。manifest 文件缺失而 receipt 完整时，可用原包摘要绑定后重建；存在但内容被改动时拒绝。

修复保持应用版本和安装实例身份；它不绕过升级要求更高版本的规则。每次确认修复创建新的 task/commit，并把 `previous_commit_id` 指向原提交，避免同一个提交身份对应不同的资源记录。使用不同内容重建的同版本包会被拒绝。

## 修复如何处理资源

有可选组件时，“受管文件”以已提交选集为准。未选择的组件不属于缺失资源，不会被修复自动安装。需要增加功能请改用“更改组件”。

| 资源情况 | 默认处理 |
|---|---|
| 受管文件存在且内容一致 | 保留 |
| 受管文件缺失 | 从原包补回 |
| 受管文件存在但摘要不同 | 保留并报告冲突 |
| 原先选择创建的快捷方式缺失 | 按原安装选择重建 |
| 系统卸载登记缺失 | 在安装归属完整可验证时重建 |
| 现有系统卸载登记与原安装不一致 | 拒绝覆盖，报告冲突 |
| 未知文件或应用用户数据 | 保留 |

摘要不同只能说明内容变化，不能证明文件损坏。显式选择恢复修改过的受管文件时，必须先备份原内容再替换，并保存备份位置；默认不会自动选择覆盖。修复报告应区分已经补回的资源、仍保留的冲突和未能完成的变更，不能把“操作结束”解释为所有文件均已恢复原版。

修复也经过准备、备份、部署、核验和提交。中途失败时尝试回退；意外退出后使用相同恢复机制处理。修复前已经缺失的文件，在回退时仍应恢复为缺失；不能把修复前的异常状态当成完整安装去伪造恢复成功。

具体命令见 [CLI 参数](cli.md) 和 [接入指南](getting-started.md)，支持边界见 [兼容约定](compatibility.md)。

## 同版本增删组件

保留原始 Setup。通过系统“更改”入口，或双击同版本同构建的原包进入维护页，在“修复安装 / 更改组件”之间切换；只有主程序的包不显示组件更改页。也可用 `--operation modify --install-dir '<原安装目录>'` 直接进入更改页。

清单初始为已安装集合。确认勾选后，新增项部署对应文件，取消勾选项仅移除内容仍与安装记录相符的受管文件。已修改文件和用户新增文件保留；不改动应用版本、安装目录和快捷方式选择。没有变化时 GUI 按钮禁用。

静默命令必须给出最终完整集合，例如：

```powershell
& '<原始Setup.exe>' --silent --operation modify --install-dir '<原安装目录>' `
  --components core,component-b --report '<新报告路径>'
```

这会保留主程序与组件 B，并移除其他原选组件的可安全移除资源。它不同时修复其他组件的既有缺失；如需补齐资源，请另外使用修复操作。更改中断后，恢复使用中断前冻结的计划和选集，不重新询问组件。配置、升级继承及旧记录迁移见[可选组件](optional-components.md)。

## 执行前的占用检查

普通操作启动 worker 前检查运行中的相关应用、受管文件占用和无法完成的系统查询。GUI 显示应用/PID和文件，用户保存工作、手动关闭应用后点击“重新检查”；静默操作退出 `3` 并生成 `NotStarted` 报告，`worker_started` 为 `false`。检查失败时不会自动终止进程、覆盖文件或创建部署事务。

恢复沿用原始任务证据和备份，不使用普通 receipt 占用预检；实际恢复遇到资源占用仍须按恢复规则处理。检查通过后新出现的占用，也仍由事务的失败/回滚规则处理。详细边界见[Windows 维护入口与占用检查](windows-maintenance.md)。
