# 可选组件设计提案

状态：**提案，尚未实现**。本文基于当前仅使用 Rust 后端的代码，说明下一阶段建议采用的行为与实现边界。下文新增的配置字段、schema 和命令参数均为拟议接口，不能用于当前发布版。

## 1. 建议结论

第一版做成：**一个离线完整包、一个必选主程序、若干平面可选组件，安装后可以增删组件。**

例如 Nimbus 笔记：主程序必装，离线帮助默认勾选，示例笔记默认不勾选。所有内容都在同一个 Setup 中；选项决定部署哪些文件，不改变下载包大小。

| 决策 | 建议 |
|---|---|
| 必选内容 | 只有保留 ID `core`；主入口、启动所需 DLL 和公共文件放在这里 |
| 可选内容 | 平面复选框；组件 ID 跨版本保持稳定 |
| 依赖关系 | 首版不支持组件间依赖、互斥或嵌套；共享依赖放入 `core` |
| 安装后的增删 | 新增独立 `modify` 操作，界面名称“更改组件” |
| 修复 | 只修复原来已选的组件，不替用户增删组件 |
| 升级 | 保留旧选择，新出现的可选组件不因默认勾选而自动加入 |
| 异常恢复 | 使用中断时冻结的原计划，不能在恢复过程中重新选组件 |
| 首版包形态 | 完整离线包；不增加下载器、独立组件版本或组件脚本 |

把“首次安装可勾选”单独交付会留下升级、卸载和维护缺口。建议分阶段开发，但以上行为一起达到验收条件后再公开发布组件能力。

## 2. 为什么不能只在界面增加几个复选框

当前代码把全部载荷视为一个整体：

- `Manifest.files` 是包内完整文件集合；`InstallPlan` 的文件数、字节数与它一致。
- `Receipt.files` 必须等于 `Manifest.files`，worker、事务执行与安装后核验都依赖这一约定。
- 原生载荷按照 manifest 顺序保存全部文件，解析时校验整个载荷。
- 升级差异比较的是新旧完整 manifest；修复和卸载也按整体安装记录处理。

如果只跳过未勾选的文件，安装器会把“没有安装”误判成“丢失需要修复”，卸载也无法准确知道自己管理哪些文件。需要先分清**包中有什么、本次选择什么、已经安装什么**。

## 3. 配置与文件归属

### 3.1 拟议配置示例

保留一个完整应用发布目录，组件只声明该目录内文件的归属。第一版只接受明确文件路径和以 `/` 结尾的目录路径，不增加通配符、排除规则或多源目录合并。

以下为拟议的 `avelin.toml` schema 2，不是当前可执行示例：

```toml
schema_version = 2

[app]
id = "dev.example.nimbus"
name = "Nimbus 笔记"
version = "1.1.0"
entry = "Nimbus.exe"

[payload]
directory = "release"

[install]
directory_name = "NimbusNotes"
desktop_shortcut = false
start_menu_shortcut = true

[[components]]
id = "core"
required = true
name = { "zh-CN" = "主程序", "en-US" = "Application" }
description = { "zh-CN" = "启动应用所需的文件", "en-US" = "Files required to run the application" }
paths = ["Nimbus.exe", "runtime/"]

[[components]]
id = "offline-help"
required = false
default_selected = true
name = { "zh-CN" = "离线帮助", "en-US" = "Offline help" }
description = { "zh-CN" = "无需联网即可查看使用帮助", "en-US" = "Read the guide without an internet connection" }
paths = ["docs/"]

[[components]]
id = "samples"
required = false
default_selected = false
name = { "zh-CN" = "示例笔记", "en-US" = "Sample notes" }
description = { "zh-CN" = "用于体验功能的示例内容", "en-US" = "Example content for trying the application" }
paths = ["samples/"]
```

对应的发布目录必须只有这些规则能够唯一覆盖的文件。例如新增了 `licenses/`，却没有把它归入 `core` 或另一个组件时，`check` 应报出未归属文件，而不是悄悄默认安装。

### 3.2 第一版校验规则

1. 组件 ID 使用小写 ASCII，拟定为 `[a-z][a-z0-9_-]{0,63}`；组件数量先限制为 32 个（包含 `core`）。显示名称可以改，ID 不随语言或排序变化。
2. 必须恰有一个 `core`，且 `required = true`；其余组件必须为可选。`core` 不接受 `default_selected = false`；默认选择字段只用于可选组件。
3. 每个载荷文件恰好属于一个组件。大小写等价路径、文件与目录冲突、重复目录覆盖，即使位于两个不会同时勾选的组件中也拒绝。
4. 沿用现有 Windows 路径与 reparse point 检查；组件规则不能越出 payload 根目录，不能占用 `.avelin`、receipt 或卸载器路径。
5. `[app].entry` 必须在 `core`；公共 DLL、公共资源放在 `core`。首版快捷方式仍是整个应用的设置，不能由可选组件新增外部文件、注册表项或任意命令。
6. 目录规则覆盖其下全部普通文件；不存在的规则、空组件、未归属文件均报错。包内全局文件数和载荷大小限制继续适用，不能用组件绕过。
7. 要求组件名称和说明同时提供 `zh-CN`、`en-US`；文案按普通文本显示，不解释 HTML、脚本或模板表达式。
8. 不支持的 `requires`、`conflicts` 等字段直接报错，不做忽略处理。构包工具无法证明应用运行时完全独立，发布者仍需验证各个支持的选集。

没有配置组件的旧 schema 1 配置继续可读，在新构包器内部归一化为“所有文件归属 `core`”。schema 2 配置也可以只声明 `core`；这时安装界面不出现没有实际选择价值的组件区。

### 3.3 为什么第一版不做依赖树

“语言包依赖离线帮助”“A 与 B 互斥”会引入自动勾选、撤销联动、循环检测和升级后的选择变更。对目前的单应用离线包，先要求可选组件各自依赖主程序即可。

确实无法拆开的内容合并成一个组件；多个组件都需要的库放进 `core`。以后有真实产品无法按此组织，再加入显式依赖图和冲突解释，不提前留一个看似支持却没有完整语义的字段。

## 4. 三份数据，各自承担一个职责

| 数据 | 保存内容 | 不能拿它推断的事情 |
|---|---|---|
| 包 manifest | 完整组件目录、默认值、全部文件及每个文件唯一的 `component_id` | 不能据此说所有组件都已安装 |
| 安装计划 plan | 本次操作、最终选集、原选集、原 receipt 摘要、所需资源差异和冻结后的统计 | 不能把当前 UI 状态当作已提交结果 |
| 安装记录 receipt | 本次成功提交的选集、受管文件及其组件归属、完整包 manifest 摘要、安装实例和提交身份 | 不能据此断言文件之后没有被用户修改 |

建议新增 `ComponentDefinition`、`ComponentSelection`、`SelectedResources` 等明确类型。`ComponentSelection` 是经过校验的完整选集，包含 `core`；序列化前按 ID 排序，拒绝重复 ID 和未知 ID。

**manifest 始终保存完整包。不要生成删减版 manifest 去冒充原包。** 原始 manifest 摘要继续绑定整个构建，文件筛选由一个公共的纯函数 `resolve_selection(manifest, selection)` 完成。

拟议的关键字段形状如下；这是省略其他必填字段的说明片段，不是完整 JSON schema：

```json
{
  "manifest": {
    "schema_version": 2,
    "components": [
      { "id": "core", "required": true },
      { "id": "offline-help", "required": false, "default_selected": true }
    ],
    "files": [
      { "path": "Nimbus.exe", "component_id": "core" },
      { "path": "docs\\guide.pdf", "component_id": "offline-help" }
    ]
  },
  "plan": {
    "schema_version": 2,
    "selected_components": ["core"],
    "selection_source": "explicit"
  },
  "receipt": {
    "schema_version": 2,
    "selected_components": ["core"],
    "files": [
      { "path": "Nimbus.exe", "component_id": "core" }
    ]
  }
}
```

具体要求：

- plan 的 `payload_file_count`、`payload_bytes` 改为最终选集中载荷资源的数量与字节数；新增或另行记录包总字节数、暂存字节数、备份字节数，避免同一个字段表示两种统计。
- receipt 的文件集必须严格等于最终选集对应的清单资源，不能只是“manifest 的某个子集”。这样漏文件、伪造归属和混入未选组件都能被拒绝。
- 文件 hash 仍表示安装器认可的原始内容。修复时保留了用户改动，不把改动后的 hash 写成原始发行内容；结果报告单独列出冲突。
- GUI、静默入口、coordinator、worker 都调用同一套选集规则。worker 独立重算选集、差异和统计，不信任调用方传入的文件列表。
- 列表顺序、显示名称、默认选择变化，不改变组件身份。相同文件不能因为组件之间共享而得到两个删除所有者。

这里的“receipt 文件集严格等于选集”是**结构和归属约束**，不是持续保证磁盘上每个文件都健康。文件在提交后可以被外部修改或删除，receipt 仍保存原始基线，修复据此发现问题。操作结束时还须进行与该操作相符的磁盘核验：安装、升级核验本次提交的选集资源；modify 核验本次增删与未变资源的实际状态；修复沿用现有“缺失已补回、修改冲突明确保留”的结果分类。不能用一次通用 hash 循环覆盖所有操作。

现有 `native_payload` 可以先保持“按完整 manifest 顺序储存全部文件”的二进制布局；依旧校验完整包，然后只暂存和部署已选文件。不要仅遍历筛选后的 manifest 去读取原载荷，否则偏移和文件 hash 会错位。manifest schema 升级与载荷二进制版本是两件事。

## 5. 各种操作的选择规则

### 5.1 首次安装

未提供显式选择时，采用 `core + default_selected 的可选组件`。用户勾选后保存的是最终集合，而不是“对默认值做了哪些增减”。计划生成后冻结选集，开始执行后不再接受勾选或迟到的 UI 回调。

只选 `core` 是有效安装；“没有任何组件”不是有效安装。首次安装只检查将部署的目标路径；未选组件的同名非受管文件不应被接管或删除，日后添加该组件时再按目标冲突处理。

### 5.2 升级

没有显式选集时：保留仍存在于新包的旧选择，加上必选 `core`。新出现的可选组件保持不选，哪怕新包设置了 `default_selected = true`。默认值仅用于首次安装。

| 变化 | 处理 |
|---|---|
| 已选组件仍存在 | 继续选择，按新版本内容升级 |
| 未选组件仍存在 | 保持未选；默认值变化不影响它 |
| 新增可选组件 | 保持未选，GUI 显示“新增”；用户可以本次主动选择 |
| 已选组件在新包中消失 | 在确认摘要列出移除；原版受管文件删除，用户修改过的文件保留并报告 |
| 组件改显示名称 | 选择不变 |
| 组件改 ID | 视为旧组件消失、新组件出现；首版不做猜测或 ID 别名迁移 |

升级差异应计算为：**旧 receipt 受管文件集合 → 新 manifest 的最终选集资源**。不能比较新旧两个包的全集，否则未安装的组件也会被当成已有资源。

路径相同、内容相同而组件归属变化时，也要在新 receipt 中原子更新归属；该路径是否留下，取决于新选集，而不是旧组件名称。升级沿用现有未知文件和修改文件冲突保护：需要写入的目标如果无法安全确认归属，拒绝并报告，不能用组件变化绕开。

消失或取消选择的组件若留下用户修改文件，它们从新 receipt 的受管文件集中移出，保留清单记录路径和实际 hash。后续卸载不能再递归清理这些文件。日后重新选择该组件遇到这些路径时，按非受管目标冲突处理，不自动重新接管。

### 5.3 更改组件：新增 `modify`

推荐独立操作，界面叫“更改组件”，而不是扩大“修复”的含义。

| 操作 | 用户意图 | 允许改变组件选择 | 允许改变应用版本 |
|---|---|---|---|
| `upgrade` | 更新整个应用 | 可以 | 必须更高版本 |
| `modify` | 添加或移除可选内容 | 可以 | 不可以 |
| `repair` | 恢复已安装资源 | 不可以 | 不可以 |
| `recover` | 处理上一次中断事务 | 不可以 | 跟随原事务 |

`modify` 必须使用安装时同一构建的完整包内容，校验 app ID、版本、完整 manifest、原 receipt 和 backend 摘要。只有版本号相同仍然不够。不同构建请提高应用版本并走升级；这里不要求外层 Setup 文件逐字节相同，详见 5.5 节。

一次更改的处理：

1. 检查没有未解决事务，并锁定当前安装实例；显示原选集与目标选集。核验安装器自己的 manifest、runtime、卸载器与登记；对保持选中的组件，记录每个文件的实际状态（存在时的大小和 hash，或缺失）。该快照与新旧选集一同冻结，开始变更前再次检查。
2. 添加组件的文件从原包暂存；移除组件的原版文件先备份，再删除。
3. 被移除组件的修改文件保留并明确告知；添加组件遇到非受管路径冲突时拒绝。
4. 未改变选择的组件不重写，允许原先缺失或已修改；操作结束时确认仍与冻结的实际状态一致。不顺手修复，也不要求用户为了添加帮助包而先覆盖自己修改的主程序配置。
5. 核验差异、登记和保留资源，写入新的 receipt；保持安装实例和应用版本，产生新的 task/commit，连接 `previous_commit_id`。
6. 出错则恢复到本次操作前的实际状态；中断后走统一恢复入口。添加、移除和 receipt 提交是一个事务。

目标选集与原选集完全相同时，返回“无需更改”，不创建伪造的安装提交。首版 modify 在确认前可以退出；执行后沿用升级的策略，不提供中途取消按钮，执行失败或意外中断仍必须能够回退或恢复。

第一版先从原 Setup 提供入口；系统应用列表的“修改”入口只有在对应启动与包来源流程实现并验证后才开放，不提前把 `NoModify` 改成可用。

### 5.4 modify 的结果核验必须独立实现

现有安装、升级结束时，会逐个检查 manifest 文件的原始 hash；直接套用这些函数会把“原先就缺失的未变文件”错误判为更改失败。第一版就必须拆分结构校验与操作结果校验，增加明确的 `verify_modify_result`，而不是只放宽入口或删掉后置检查。

| 对象 | 更改后的核验 |
|---|---|
| receipt | 等于计划生成的候选结构；选集资源完整，包含未变组件的原始基线；安装实例与提交链正确 |
| 新增组件 | 每个应部署文件存在且与新包基线相符；不能把缺失文件算安装成功 |
| 已移除的原版资源 | 确认已删除；操作前缺失的仍保持缺失 |
| 已移除但被用户修改的资源 | 确认与操作前快照一致；列入保留清单，从新 receipt 归属中移出 |
| 仍被选择的原有组件 | 存在的文件与冻结的实际大小和 hash 一致；原先缺失的仍缺失。此处不拿发行原版 hash 替代实际快照 |
| 内部资源、登记与快捷方式 | 核验本次计划要求的结果及受管身份；不把安装器内部缺失/身份冲突按普通用户修改放行 |

例如帮助包已成功添加，但主程序某个受管配置在更改前就被修改：新的 receipt 仍保存该配置的原版 hash，以便今后修复发现差异；modify 的结果明确报告“组件已更改，原有修改保留”。已有缺失项也须报告，不能显示“所有文件已恢复”或把不存在的入口作为可成功启动的程序。

实际状态快照、观察到的缺失、受影响资源差异都要写入恢复记录并绑定任务，提交后恢复使用同样的操作级核验。回退恢复本次触及的资源，未触及的资源不能因为和原版不同而被顺手重写；这是首版必须实现的部分。获得产品锁不等于阻止应用或其他程序写文件：开始前发现快照变化就停止；已变更后发现外部变化而不能证明结果时保留证据并报告待检查状态，不能覆盖新变化来制造“恢复成功”。

### 5.5 同一构建与同一安装怎样确认

当前修复代码真正核对的是 manifest 内容和 Rust backend 的摘要；它没有把外层 Setup 的完整文件 hash 作为安装身份。组件维护应延续这个区分：

| 层次 | modify 的核对规则 |
|---|---|
| 包内容 | 完整 manifest 按对应版本的固定序列化规则计算摘要，与 receipt 一致；其 runtime 摘要、完整载荷各文件大小和 hash 全部验证 |
| 执行程序 | 提取出的完整 backend（worker + 嵌入内容）摘要等于 receipt 的 `uninstaller_sha256`；冻结后的计划明确绑定该 backend 摘要，worker 核对自身 |
| 安装实例 | app ID、应用版本、当前 Windows SID、规范化安装根目录与 receipt、现有登记一致；保持同一 `installation_id`，不接受同产品的另一个目录 |
| 原状态 | plan 绑定原 receipt 的原始字节摘要和原 commit，执行前再核对；目录及相关输入继续使用现有固定句柄和 reparse 防护 |
| 新任务 | 新 task/commit，`previous_commit_id` 指向原提交；选集、差异、原状态和包身份一同冻结并绑定到本次会话 |
| 进程与恢复 | 沿用产品锁、管道对端 PID、创建时间和可执行文件身份校验；恢复只接受这个任务的计划、备份与提交证据，不能挪到另一个根目录 |

外层 Setup 必须通过正常容器校验，提取出一致的 manifest 和 backend；但不用要求外层文件逐字节相等。未来若外层签名或允许的封装信息发生变化，只要读取器合法支持该容器、上述内容完全一致，就不应仅因外层 hash 不同判成另一个构建。**这不是忽略容器校验，也不是允许重新签名或替换内部 worker 后绕过 backend 摘要**；内部 backend 字节变化仍属于不同维护输入。签名容器格式本身的支持不在本提案内。

另外，当前已安装的 `uninstall.exe` 实际保存完整 Rust backend，包含 manifest、runtime 和全部原生载荷。以后若接系统“修改”入口，应先评估复用这个已受 receipt 摘要约束的输入，无需先设计第二份大包缓存。首版使用原 Setup 只是限制入口范围；已安装 backend 丢失或不符时，仍需要匹配包执行修复或明确拒绝。

### 5.6 修复、恢复、卸载

- **修复**：选集严格来自 receipt；不读取当前默认值，不显示可编辑组件框。未选组件缺失是正常状态。原有显式覆盖修改文件策略只用于既有受管文件。
- **恢复**：记录原计划、前后选集、完整包摘要、前后 receipt、差异、备份及提交证据。恢复时不重新运行默认选择规则，不接受 `--components`，继续得到可验证的提交前或提交后状态。
- **卸载**：只按 receipt 管理实际安装过的组件与内部资源；保留未知文件、用户数据和内容变化的文件。不遍历完整包文件集去尝试删除未选组件，更不能递归删除组件目录。
- 存在未完成事务时，安装、升级、更改、修复和卸载都先被阻止，按现有恢复规则处理。

## 6. 静默参数必须没有“空选择”歧义

推荐增加一个表示**完整最终选集**的参数 `--components`，不用 `--add` / `--remove` 两套增量规则。以下命令均为未来接口：

```powershell
# 首次安装：使用发布者默认选择
.\Setup.exe --silent --install-dir C:\Apps\Nimbus

# 首次安装：明确只安装主程序
.\Setup.exe --silent --install-dir C:\Apps\Nimbus --components core

# 更改为主程序 + 离线帮助；示例组件若原来存在，则移除
.\Setup.exe --silent --operation modify --components core,offline-help

# 升级：保留旧选择；不自动接受新组件默认值
.\Setup-New.exe --silent --operation upgrade
```

| 输入 | 语义 |
|---|---|
| 安装时省略 `--components` | 使用包默认选择 |
| 升级时省略 | 保留旧选择，排除新包已经没有的 ID |
| GUI 更改时省略 | 以旧选择初始化页面，等待用户确认 |
| 静默更改时省略 | 参数错误，要求明确目标选集 |
| `--components core` | 显式只选主程序，不等于采用默认值 |
| 空串、只有逗号、重复 ID、未知 ID、缺少 `core` | 参数错误，开始变更前退出 |
| repair / recover / uninstall 传入 `--components` | 参数错误；这些操作的范围由安装记录决定 |

不增加 `all`、`none` 这样的特殊 ID；脚本写明完整 ID 列表。这样以后发布者新增组件时，已有脚本不会无声扩大安装范围。计划和报告记录 `selection_source`（默认、继承、显式或旧版迁移），但执行授权始终以冻结后的完整选集为准。

## 7. 界面与空间检查

有可选组件时，在现有准备页加入“安装内容”区：每行名称、说明和部署大小。主程序显示“必选”且不能取消；可选项用标准复选框。组件较多时在区域内滚动，保留目录、确认项和开始按钮可见，避免另做一套安装向导。

升级页标出新增、保留、移除；同版本原包提供“修复安装”和“更改组件”两个明确入口。提交前摘要显示“将添加 / 将移除 / 保持不变”，不能只显示所有可选内容的总大小。

无障碍要求：

- 中英文名称、说明、必选状态、勾选状态和大小都有可读文本；不能只靠颜色或图标区别。
- Tab 顺序稳定，Space 切换当前可选项；必选项的可访问性名称解释不能取消的原因。
- 勾选后焦点不跳走；适度朗读选中数量和空间变化，不逐帧重复播报。
- 开始执行后锁定选择；返回错误或取消后的选择仍有明确来源。迟到回调不能修改冻结的任务。

空间分开显示和计算：

1. “应用占用空间”根据最终选集计算，可另显示本次增加或释放的字节数。
2. 真正能否执行，要按卷汇总目标部署、暂存、备份和安装器内部文件的峰值需求，使用溢出检查。
3. 当前完整离线 backend 在会话目录中的复制仍包含所有组件，安装目录的 `uninstall.exe` 也保留完整 backend；完整包校验仍会读取所有组件。部署选集减少不等于整个目标占用等量减少。不能把临时空间直接等同于选集大小，不能承诺取消勾选能减少下载量。
4. UI 预估不代替执行前检查；获得产品锁后再次计算并检查真实空间，不在磁盘已变更后才发现漏算旧文件备份。

这属于选择正确性和避免磁盘写入失败的必要检查，不扩展成性能优化或性能测试项目。

## 8. schema 与旧安装兼容

不要只把全局 `SCHEMA_VERSION` 从 1 改成 2，然后让所有记录一起换号。当前 manifest、plan、receipt 与恢复日志共享部分模型，但恢复记录本身已经使用 schema 2；它们应有独立版本常量和明确的转换边界。

建议：

- 新组件配置、manifest、plan、receipt 使用各自 schema 2。新包即使只有 `core`，也使用新 manifest 与匹配的 runtime/worker。
- 新代码保留 schema 1 的只读模型和严格验证；进入内部统一模型时，将旧全部文件映射为隐含 `core`。旧 receipt 摘要绑定原始字节；旧 manifest 摘要按旧版本既定的序列化规则计算。不能加入新字段后重新序列化，再与旧摘要比较。
- 新恢复记录因为嵌入 plan、receipt 和选集，另升到恢复 schema 3；现有 schema 2 恢复记录按原规则处理，不能机械转换未完成事务。IPC 也要明确支持 `modify`，执行前确认双方兼容。
- 旧 runtime 对新 manifest/schema、旧 worker 对新计划必须在受管资源变更之前拒绝。不能为了兼容而隐藏新字段或沿用 schema 1；否则旧卸载器可能把整个包当成已安装文件。

### 8.1 schema 1 安装怎样第一次升级到组件包

旧 receipt 没有组件选择。直接映射为“只选 core”可能删掉原来安装的帮助文件；直接采用新默认值又可能加入从未安装的新内容。也不能仅凭一个旧路径重叠就继承整个组件：一个组件可能包含 1 个旧文件和 500 个全新文件。

第一版建议**自动迁移只处理可明确对应的情况，模糊情况要求明确选集**，不增加专门的迁移配置语言：

1. 严格核验旧 Rust 安装的 manifest、receipt、安装实例、登记与当前用户，保留其原始记录；未完成事务先恢复。
2. 新选集从 `core` 开始。对新包每个可选组件，如果它的**全部文件路径**都能在旧 receipt 中找到，才可自动继承为已选；比较采用现有 Windows 路径规则。文件内容随应用升级而变化，仍按正常升级处理。
3. 完全由新路径组成的组件保持不选，即使它默认勾选。若一个组件混有旧路径和新路径，则标记为“迁移需要确认”，不自动加入、不直接默认为移除。旧文件在新包中消失时，按正常升级的删除/保留策略处理。
4. 路径对应用于选择建议，不用于信任文件内容。所有原有归属和 hash 检查仍然执行；修改过的旧文件不能因此被覆盖。
5. 没有模糊组件时，GUI 与静默均可使用确定规则，并在报告记录选择来源。有模糊组件时，静默省略 `--components` 必须在变更前拒绝，提示传入完整选集；显式选集按正常升级规则校验。
6. GUI 对模糊组件展示旧文件、新增文件及选与不选的后果，提供建议但要求用户明确确认最终完整选集；仅沿用普通“开始升级”按钮的默认状态不算迁移确认。其余迁移及资源删除也必须出现在最终摘要中。
7. 这次升级成功提交后才写 schema 2 receipt，保持安装实例身份并连接旧 commit。升级失败回退时还原原字节的旧 receipt、manifest 和卸载器。

这个规则会保留路径稳定的旧内容，但无法识别完全换路径后的同一功能；完全新路径的组件也许只是旧功能搬家，首版仍不猜测。发布者首次引入组件时应尽量保持路径稳定；确实搬迁或混合新旧内容时，接入测试必须检查删除/增加摘要，并通过明确选集交付迁移指引。

权衡是某些旧版静默升级需要补一个 `--components` 参数。这个成本比悄悄扩装更容易解释，也比增加 `legacy_component_map` 等专用配置和版本匹配规则更小。若多个真实产品反复需要同样的复杂迁移，再设计经过校验的发布者迁移声明；第一版不预埋未经验证的自动映射能力。

已安装 schema 2 后，不支持由旧 runtime 维护或降级回旧包；旧工具应清楚拒绝。已有 schema 1 原包对已有 schema 1 安装的维护能力继续独立存在。

| 位置 | 工作 |
|---|---|
| `crates/avelin-core/src/lib.rs`、`model.rs` | 分离版本、旧模型兼容、组件与选集校验、文件归属、新 `Operation::Modify`、选集差异 |
| `apps/avelin-cli/src/config.rs`、`init.rs`、`native_builder.rs` | TOML 分类、穷尽归属检查、构建完整组件清单；`init` 默认仍生成简单主程序配置 |
| `crates/avelin-core/src/native_payload.rs` | 保留完整布局与完整 hash 校验，给执行层提供稳定文件索引 |
| `apps/avelin-app/src/coordinator.rs`、`upgrade.rs`、`maintenance.rs` | 参数、选集来源、旧版迁移、原包校验、计划/receipt 生成、空间检查；拆分结果核验，新增 modify 的实际状态快照核验 |
| `crates/avelin-engine/src/worker.rs`、`transaction.rs` | worker 独立验证；部署选集，按 receipt 卸载；执行 modify 的原子增删 |
| `crates/avelin-engine/src/recovery.rs` | 新记录冻结选集与资源差异，保留旧恢复路径；中断后确认提交或回退 |
| `crates/avelin-ui/src/lib.rs`、`state.rs`、`view.rs` | 组件状态、列表与摘要、维护入口、异步状态冻结和键盘操作 |
| `crates/avelin-core/src/locales/`、`docs/schemas/` | 中英文系统文案、schema 和正反例；品牌文案与组件文案分开验证 |

注意 `apps/avelin-cli/src/components.rs` 当前负责寻找 CLI 旁的 runtime/worker 二进制，**不是可选安装组件模型**。新代码应放到含义明确的模块，避免两个概念同名造成误用。

## 10. 实施顺序与验收

### 阶段 A：先锁定模型与兼容

完成配置、完整 manifest、选集解析、receipt 归属、schema 1 迁移规则以及纯模型测试。保留无组件项目的接入方式。先验证模型中的“未安装”不会被解释成“丢失”，再接执行层。

### 阶段 B：打通真实事务

完成首次选择、选择保持的升级、receipt 范围卸载、只修已选组件和 `modify`。将选集加入任务绑定、worker 独立校验、提交核验和恢复记录；同时覆盖首次安装取消、事务失败、进程中断和恢复再次中断。

### 阶段 C：完成使用入口

接 GUI、静默参数、中英与键盘无障碍、空间摘要、报告和公开文档。用一个有 `core`、帮助和示例的 Nimbus 样例交付完整包。先从原 Setup 打开维护入口，系统“修改”按钮后续按实际需要接入。

### 最低测试矩阵

| 范围 | 必须证明的行为 |
|---|---|
| 构包 | 只含 core、多个组件可用；重名 ID、未归属/重复路径、目录交叉、入口在可选组件、reparse 与越界路径均拒绝 |
| 选择 | 默认与显式 core 不同；未知/重复/空选择拒绝；参数、GUI 与 worker 得到同一最终资源集 |
| 首次安装 | core、默认选集、全部三个选集分别核对真实文件、receipt、快捷方式与卸载结果；未选文件确实没有被部署 |
| 升级 | 旧选择保留、新默认不暗加、已选组件消失、组件归属移动、显式改变选集、修改过的移除文件保留 |
| 更改组件 | 加入、移除、同时增删、相同选集无操作；保留组件缺失/修改保持实际原状且不阻止其他组件增删；操作中外部再修改不覆盖；原包不一致拒绝；未知目标冲突不覆盖 |
| 修复与卸载 | 只修已选；未选文件缺失不算故障；卸载不碰未选同名文件；修改文件与用户数据保留 |
| 事务 | 在添加文件后、删除文件后、提交前和提交后中断；恢复遵循旧选集或新选集；重复恢复与恢复再中断不重复破坏资源 |
| 防篡改 | 篡改 plan 选集、file_count、归属或 receipt 被 worker 拒绝；恢复不接受当前 UI 或命令行新选集 |
| 兼容与包身份 | schema 1 全旧/全新/混合路径分别处理，混合时静默拒绝或显式选择；迁移失败回退原字节；同内容合法外壳与不同backend的区分；旧 runtime 拒绝新包；旧恢复记录仍按原规则核验 |
| 空间与界面 | 选集统计、分卷暂存/备份估算、溢出与空间不足；一次本机中英/键盘/讲述人检查覆盖组件名称与勾选状态 |

使用有代表性的组合与边界，不对 31 个可选组件跑全部排列。现有核心流程应继续回归；只有失败、代码变化或未解决问题才重复相关检查。

完成标准：开发者能声明组件；用户能选装、升级保留选择、同版本增删、修复和卸载；任一中断都按冻结记录恢复；已有 schema 1 Rust 安装可按明确规则升级。性能、签名、独立环境与重复缩放检查继续沿用项目已确定的暂缓安排。

## 11. 进入实现前保留的决策

本提案已给出默认建议，不需要先为每个细节来回确认。真正可能改变范围的只有两件事：

1. 第一个真实应用是否有无法放入 `core` 的可选组件相互依赖。如果有，再评估依赖图是否必须进入首版。
2. 用户是否必须从 Windows 应用列表直接进入“更改组件”。如果有，应优先复用已安装并经过摘要核验的完整 backend，补齐对应启动与缺失包处理；不预设另外长期缓存一份大包。

没有这两类明确需求时，按本文的平面组件、保留原包、独立 modify 路线实施即可。
