# 预览版兼容约定

本文说明当前源码的输入、运行行为和证据边界；不是全 Windows 环境认证或长期稳定 API 承诺。已发布的 `0.1.0-preview.1` 二进制不包含新增可选组件能力，使用组件须配套构建当前源码。接入步骤见[接入指南](getting-started.md)，源码构建见[开发指南](development.md)。

## 1. 工具包与产品版本

工具包版本、应用版本和数据 schema 是三个不同概念：

| 标识 | 含义与使用方式 |
|---|---|
| `0.1.0-preview.1` | 预览工具包的交付身份；以包内组件清单、逐文件 SHA-256 和外部归档摘要识别 |
| `app.version` | 被安装产品的 SemVer 版本；参与同产品升级判断 |
| `schema_version = 2` | 当前 TOML 配置、manifest、plan、receipt 的组件结构版本；保留支持范围内的 schema 1 读取 |
| `protocol_version = 1` | 后端传输负载的当前协议版本；仍需任务、顺序和对端身份验证 |

每次工具包记录实际 runtime、CLI、Rust worker 和样例摘要。不要按同名文件混搭不同构建的组件；普通 PR 源码检查不执行完整安装链。所有执行组件均为 Windows x64。

`build` 仅使用 Rust，引擎选择参数已移除。原生载荷目前未压缩；每层嵌入区域不超过 1 GiB、manifest 不超过 32 MiB，组件与元数据计入开销。现有 Rust 安装身份、登记键与 receipt 规则保留。

旧 NSIS 源码、构包入口和运行支持已经移除。旧版独立 Setup 仍包含自己的执行组件；当前版本不接管旧 NSIS 安装，也不执行其事务恢复。需要用原卸载器卸载，再安装新 Rust 包。

## 2. 配置与展示资源

当前 `avelin.toml` 使用 `schema_version = 2`，包含 `[app]`、`[payload]`、`[install]`、`[[components]]`，可选 `[ui]`。旧 schema 1 配置不接受组件字段，全部载荷归为主程序。未知字段或不支持的 schema 明确拒绝；拼错配置不会被当作已生效的选项。完整命令契约由 [CLI 说明](cli.md) 维护。

- `app.id` 是稳定产品身份，当前允许 1–100 个 ASCII 字母、数字、点、下划线或连字符。名称和版本不是安装身份的替代物。
- `app.entry` 必须是载荷清单内的相对路径；载荷来自发布目录。重解析点、越界路径、Windows 等价路径冲突及安装器保留资源均受校验。
- 快捷方式配置是包默认值；GUI/显式 CLI 布尔参数形成本次实际选择。升级默认读取旧 receipt 的实际归属。
- 可选组件是平面文件组，唯一必选 ID 为 `core`。首次安装采用默认或显式选择，升级继承原选集，新可选项不自动加入。包始终包含所有组件，选择不改变下载大小，详见[组件指南](optional-components.md)。
- 展示模板当前只有 `compact`；内置中英语言，自动语言选择有明确 fallback；仅注册的文案键和正确占位符可覆盖。
- logo 是构建时读取并嵌入的静态 PNG，最大 512 KiB，宽高各不超过 1024 像素；品牌色为 `#RRGGBB`。语言目录只接受 `zh-CN.json`、`en-US.json`。运行时不读取构建机的配置路径或任意远程 URL。

`check` 验证配置、资源及清单，不执行安装；`build` 生成包，不因构建成功而证明产品可运行或可升级。输出须使用新的路径，避免覆盖既有包及其配套证据。

## 3. 安装、升级与用户数据

当前范围为同一当前用户、普通桌面应用、单个离线完整包；由 Rust 引擎执行，提供显式中断恢复与同版本修复。未提供全用户安装、服务/驱动安装、差分更新、在线版本发现或任意脚本钩子。

| 操作 | 当前约定 |
|---|---|
| 新安装 | 可以存在无关用户内容；新载荷及安装器受管路径冲突必须在写入前拒绝。当前用户同产品只管理一个位置 |
| 升级 | 同产品、同 SID、固定安装目录，严格更高 SemVer 优先级；忽略 build metadata，同版本、降级及身份冲突均拒绝 |
| 归属卸载 | 只移除身份、路径与摘要匹配的受管资源；修改过的载荷/快捷方式和未知内容保留，可正常报告已卸载 |
| 卸载后重装 | 保留的用户文件允许存在；若仍占据新载荷或受管路径，则拒绝覆盖，交由接入方明确处理 |
| Rust 修复 | 完整 receipt 与原包绑定，版本和位置保持不变；补缺失资源，默认保留修改内容。显式覆盖受管修改项前先备份 |
| 组件更改 | 同版本同构建原包、固定安装目录，明确完整目标集合；只变更组件差异，保留用户新增或修改内容及快捷方式选择 |
| Rust 恢复 | 原任务退出后检查完整持久证据；未提交变更回退，已提交结果核验确认；证据不足或外部冲突时保留现场 |

升级保留 `installation_id`，生成新 task/commit，并将 `previous_commit_id` 指向旧提交。新版本不再管理的修改文件可以保留并退出新归属；新版本仍需占用的修改文件或选中快捷方式会阻止升级。仅改变 Windows 等价路径拼写，或文件与目录相互切换，当前明确拒绝。

升级前还会校验旧卸载 backend 的原生 Rust 载荷与 manifest，拒绝非 Rust 安装或缺少必要完整性字段的早期实验记录。

程序应将可变数据与只读发布载荷区分开。Avelin 不提供数据库迁移、用户配置合并或“卸载时删除全部个人数据”的通用策略；接入前必须约定数据位置和保留行为。`preserved_resources` 记录已识别的修改受管资源，不是全部未知用户数据的完整清单。

可见 Rust Setup 检测已有同产品后，根据未完成事务、相同包内容或更高版本进入恢复、修复或升级确认。同版本维护页在有可选组件时可切换“更改组件”。静默执行仍需明确选择操作；静默更改必须传完整 `--components`。安装支持受控取消；升级、卸载和维护操作没有活动取消能力，活动窗口关闭不会伪造取消成功。成功后的应用启动必须由用户明确操作，`launch_result` 不改写已确认的任务终态；组件更改不同时修复已有缺失资源，结果页不提供启动动作。

## 4. 退出码与结果判断

工具命令与安装任务的退出码用途不同：

| 入口 | 退出码 | 含义 |
|---|---|---|
| `avelin-cli init/check/build/replay/diagnose` | 0 | 该工具命令完成；`diagnose` 返回 0 不代表安装健康 |
| 同上 | 1 | 操作或校验失败；查看标准错误和保留输出 |
| 同上 | 2 | 参数解析失败；查看用法提示 |
| `avelin-cli recover` | 0 / 2 / 3 / 4 | 成功启动原 Setup 后转发其退出码；CLI 自身校验或启动失败另返回 1 |
| Setup/runtime 已启动任务 | 0 | 已确认 `Succeeded`；须关联本次报告及任务身份 |
| Setup/runtime 已启动任务 | 2 | 已确认 `Cancelled`；不适用于升级或卸载 |
| Setup/runtime | 3 | 前置拒绝、已确认失败或运行界面错误；不能一概解释为“没有变更” |
| Setup/runtime | 4 | `Unknown`，执行、恢复或结果无法确认；保留现场诊断 |

Setup 的参数解析也可能返回 2；用户在开始前正常关闭窗口可能返回 0，却没有执行任务。任务报告中的 `exit_code` 是后端观察值，`coordinator_exit_code` 是协调层结果；外部实际进程退出码应另行采集，不能由报告字段推算。GUI 在任务成功后自身出错时，进程错误与已保存的任务成功可能同时存在。

自动化应核对目标 task、operation、报告终态、进程结果和所需资源，不仅检查一个数字。显式启动记录证明入口核验及进程创建，不证明被安装应用业务功能正常。

## 5. 持久模型与恢复边界

详细字段见 [架构](architecture.md)与[本地 schemas](schemas/README.md)。schema 通过只能证明结构，不能证明当前用户、路径、摘要、磁盘状态或资源归属。

- 保留既有 receipt 所需字段；`installation_id` 仍必填。`previous_commit_id` 可缺省，新版可读取已经验证的旧记录；不由此承诺旧运行时可读取新增升级字段。
- `InstallPlan.operation = upgrade` 或 `modify` 必须携带完整 `UpgradePlan`。更改绑定相同版本、原包和操作前资源快照；安装、卸载、修复和恢复不能携带它。计划不是可由外部修改后任意重放的部署指令。
- schema 2 的 Manifest 是全包目录，Plan 冻结目标选集，Receipt 只声明已提交选集的受管文件。旧 schema 1 迁移遇到有歧义的文件映射时需要 GUI 额外确认或静默显式选集，不能按新包默认值猜测；旧运行时不保证识别新模型。
- 当前解析器拒绝未知持久字段和 schema。更高版本文件不得擅自删字段、改版本号或修摘要来绕过验证。未来不兼容变更必须显式迁移并留证；预览阶段不承诺任意历史实验产物可升级。
- 后端先暂存、备份，再变更，最后发布完整新 receipt；协调层核验提交证据。多文件与登记更新不是单个原子事务。
- 活着的后端可尝试有限进程内回滚；未确认结果报告 `Unknown`，保留会话、备份和事务标记。Rust 的显式恢复入口可在原进程退出后重新核验并处理 schema 2 事务；不删除标记直接续装，不提供任意断点续跑。
- Rust 引擎使用持久操作日志和 `.avelin/upgrade-state.json` 事务标记；该标记也用于保护安装、卸载和修复变更。schema 2 的 `engine-recovery.json` 绑定原计划、会话、变更前后资源、备份及登记快照；注册表逐步记录意图和完成状态，`engine-commit.json` 为持久提交判据。重开后先恢复未完成事务，再允许新的变更。
- 已完成提交但终态无法确认仍可能返回 `Unknown`；不能据此认定“未安装”或直接回滚。读取持久记录并核验实际资源后再决定处理方式。

`diagnose --session` 是只读观察。历史成功升级已被卸载后，当前文件和登记会显示缺失，可能得到 `NeedsReview`；这不改写当时保存的成功结果。有限恢复实现不代表全部故障路径均已验证。

`recover --check` 只检查；`recover --apply` 才执行。恢复重新验证原进程已停止、当前用户、产品互斥、每项变更及最终状态后解除遗留锁和标记。旧 schema 1 Rust 事务缺少新证据，不自动迁移为可恢复任务。相同产品后续已经发生其他操作时，不可把旧会话作为任意回退点。

修复需保留完整 receipt；manifest 文件缺失时可由相同原包与 receipt 绑定重建，存在但被改动时拒绝。包内容摘要证明一致性，不代表发布者身份。报告里的 `RepairPreservedConflicts` 表示仍有修改项未恢复，不能解释为完整修复。流程和备份规则见[恢复与修复](maintenance.md)。

## 6. 当前支持与尚未交付范围

工具包是未签名预览产物。本机及源码 CI 的结果只支持对应组件、输入与执行范围；编译 GUI runtime 和 headless UI 测试不等于原生窗口或干净 Windows 通过。

当前验收入口覆盖生命周期、中断、恢复/修复，以及独立的组件安装/更改/升级/恢复流程。中断只验证脚本列出的暂停点，不能外推任意指令中断或机器重启。范围和复现命令见[开发指南](development.md#rust-引擎真实进程验收)，后续能力见[路线图](roadmap.md)。

Nimbus A/B 只是同一测试样例的两个版本。真实产品的发布目录、运行库、功能与数据保留需要分别验证；第三方清单生成成功也不等于完整二进制分发资格确认。
